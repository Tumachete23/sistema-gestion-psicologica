# HU-003 / HU-004 — Jerarquía y aislamiento

## Estructura

La base compartida del monolito modular vive en `backend/app/Modules/Tenancy`:

- `Models/Organization.php`: raíz, aislada por su ID.
- `Models/Clinic.php`: organization_id obligatorio; visibilidad limitada a la clínica del usuario.
- `Models/User.php`: organization_id y clinic_id obligatorios. Reemplaza la ubicación inicial app/Models/User.php; auth.php y UserFactory apuntan a la nueva clase.
- `Concerns/BelongsToTenant.php`, `Scopes/TenantScope.php`, `TenantContext.php` y `TenantBuilder.php`: filtros, contexto y protección de escrituras.

Patients, Clinical, Scheduling, Billing, Documents, AI y Audit siguen reservados para sus historias; no se crearon entidades clínicas, endpoints de negocio ni funcionalidades de esas fases.

## Invariantes

- Cada consulta Eloquent normal filtra por organización y, por defecto, clínica. Organization es la excepción estructural: no pertenece a una clínica. Clinic utiliza su ID como clínica.
- Sin usuario ya autenticado, las consultas devuelven cero filas y save/create/delete arrojan AuthorizationException. No se obtiene el tenant de headers, parámetros ni payloads.
- organization_id, clinic_id e id se descartan del mass assignment, incluido forceFill. En nuevas entidades, el tenant se asigna desde el usuario autenticado al guardar.
- La pertenencia de registros existentes es inmutable. También se verifican objetos cargados previamente y saveQuietly/deleteQuietly.
- El scope se aplica a route model binding; los IDs ajenos producen 404. Las rutas de verificación existen únicamente en tests.
- Las actualizaciones masivas no pueden cambiar IDs de pertenencia, incluso mediante operaciones aritméticas. Upsert se rechaza porque omite el flujo de creación y puede resolver conflictos contra filas ajenas.
- La clave foránea compuesta users(organization_id, clinic_id) → clinics(organization_id, id) impide combinaciones entre organizaciones incluso en SQL. Las eliminaciones de raíces con referencias se restringen.
- No hay excepción de aislamiento para el nombre “Superadmin”. No se han implementado roles.

## Migración y datos de ejemplo

`2026_09_30_000003_create_tenant_hierarchy.php` es aditiva y conserva la migración original de users. Si users ya contiene registros, se detiene antes de crear tablas o columnas: es necesario acordar un backfill explícito. No asigna usuarios antiguos a una organización arbitraria ni borra datos.

`DevelopmentTenantSeeder` crea una organización, una clínica y un usuario con el nombre “Superadmin de prueba”. Es idempotente, transaccional y se limita a consola local/testing. La contraseña se genera aleatoriamente, no se imprime y no se reemplaza al repetir el seeder. Este usuario es un fixture, no una cuenta con login o privilegios implementados. Si el email de ejemplo pertenece a otro tenant, el seeder se detiene.

Para una base de desarrollo vacía, usando el PHP configurado de Laragon:

```powershell
Set-Location 'E:\Pagina Web\Sistema de gestión psicológica\backend'
$env:PHPRC = 'E:\Pagina Web\Sistema de gestión psicológica\.local\php\php.ini'
$php = 'C:\laragon\bin\php\php-8.3.30-Win32-vs16-x64\php.exe'
& $php artisan migrate --no-interaction
& $php artisan db:seed --class=DevelopmentTenantSeeder --no-interaction
```

Estos comandos de desarrollo se documentan para uso explícito; durante esta implementación las migraciones y seeders se ejecutaron solo en bases de prueba aisladas. No se modificaron .env, APP_KEY ni datos de desarrollo.

Las factories se usan dentro de `app(TenantContext::class)->provision(fn () => User::factory()->create())` para preparar fixtures. El contexto se restaura con finally y está registrado como scoped; no es una API para cambiar de tenant en peticiones.

## Casos que deben acordarse antes de HU-005

1. **Visibilidad entre clínicas:** se adoptó el valor restrictivo (solo la clínica propia). El acceso a varias clínicas requerirá una decisión explícita y no debe resolverse deshabilitando el scope.
2. **Resolución inicial del usuario:** TenantContext solo acepta un usuario ya cargado en el guard, evitando recursión al consultar User. HU-005 deberá resolver la identidad de forma controlada antes del acceso al dominio; todavía no hay login funcional.
3. **Usuarios anteriores:** se necesita una correspondencia organization/clinic antes de aplicar la migración a una base con usuarios existentes.
4. **Email:** se conserva la unicidad global de la tabla users inicial. Permitir el mismo email en diferentes organizaciones requiere definir también cómo se selecciona la organización al iniciar sesión.
5. **SQL y procesos fuera de HTTP:** un Global Scope no es una política RLS de PostgreSQL. DB::table, SQL directo, toBase, joins manuales contra tablas ajenas, insert masivo y withoutGlobalScopes pueden eludir protecciones de Eloquent. No deben usarse con payloads para acceso de negocio; las futuras importaciones/jobs necesitarán servicios con contexto explícito y pruebas propias. Las relaciones Eloquent son el camino habitual. El test recorredor detecta ausencia del trait, no demuestra la seguridad de SQL arbitrario.
6. **Administración transversal:** crear nuevas organizaciones/clínicas desde HTTP o permitir acceso global de Superadmin queda pendiente del modelo de autorización; actualmente solo se permite preparar fixtures locales/de test.
