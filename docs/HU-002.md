# HU-002 — CI mínimo

Workflow: `.github/workflows/ci.yml`. Se ejecuta en todos los push y pull requests, con dos jobs independientes. No incluye despliegues ni funcionalidades de HU-003.

## Backend

PHP 8.3 y Composer 2 respetan `composer.lock` y su plataforma PHP 8.3.30. El runner instala las dependencias de desarrollo y ejecuta:

```bash
composer install --no-interaction --prefer-dist --no-progress
php artisan config:clear --env=testing
php tests/ci-bootstrap.php
php artisan migrate --env=testing --force --no-interaction
php vendor/bin/phpunit --configuration=phpunit.ci.xml
php vendor/bin/pint --test
```

PHPUnit es el motor instalado; no es Pest. Pint es obligatorio cuando está instalado. PHPStan se ejecuta condicionalmente si existe `vendor/bin/phpstan`; actualmente no forma parte de las dependencias. Los errores de estas herramientas no se silencian.

Cada job obtiene servicios nuevos PostgreSQL 17 y Redis 7.4. La base `sgp_test` pertenece al servicio efímero, sin volúmenes ni conexiones a desarrollo. Por eso se usa `migrate`, sin `migrate:fresh` ni borrado de bases. El paso previo comprueba el entorno testing, conexión pgsql, nombre configurado y nombre real de la base, ausencia de DB_URL y disponibilidad de Redis antes de las migraciones y de PHPUnit.

`phpunit.ci.xml` selecciona PostgreSQL. `phpunit.xml` conserva SQLite en memoria para las pruebas locales habituales. El job define las variables de entorno directamente, utiliza `CACHE_STORE`, Predis y prefijos propios. No sobrescribe `.env`, no copia valores de desarrollo ni regenera APP_KEY: TestCase crea una clave efímera en memoria.

## Frontend

Node 24 satisface el requisito `>=22.12.0` de package.json. Los pasos obligatorios son:

```bash
npm ci
npm run lint
npm test
npm run build
```

Se añadió ESLint y el script lint porque no existían. `npm test` ejecuta `node --test`; no admite el argumento `--run` propuesto para otros runners. El build ejecuta Vite. Ningún paso usa `continue-on-error`, `--if-present` ni mecanismos para ignorar errores: un fallo de lint, tests o build hace fallar el job y el workflow.

## Diferencias frente a la propuesta

- Node 24 en lugar de 20, conforme a engines.
- Tests con `npm test`, sin `--run`; lint real y obligatorio.
- Configuración PHPUnit separada para evitar que la suite de CI use SQLite.
- Variables explícitas de testing y verificación de aislamiento, sin duplicar entradas de `.env.example`.
- Caché de descargas Composer; las dependencias se instalan desde el lock en cada ejecución.
- Pull requests de cualquier rama y servicios alineados con PostgreSQL 17/Redis 7.4 del proyecto.
- El archivo `ci.yml` de la raíz se conserva como propuesta; GitHub ejecuta únicamente el ubicado en `.github/workflows/`.

## Validación local

La sintaxis se verifica con `actionlint -no-color .github/workflows/ci.yml`. Los comandos de frontend se ejecutaron en Linux con `node:24-bookworm-slim`: lint, tres tests y compilación Vite correctos.

La validación backend usa una copia descartable del proyecto, PHP 8.3.30 de Laragon y contenedores exclusivos de PostgreSQL/Redis con puertos dinámicos. No usa las bases de desarrollo. Los comandos son los del job, con esos puertos y el php.ini local habilitando pdo_pgsql.

Resultado: las tres migraciones estándar se aplicaron a `sgp_test` inicialmente vacío; PHPUnit pasó 3 tests y 4 aserciones; Pint pasó. La prueba negativa con `DB_DATABASE=wrong_database` fue rechazada antes de conectar. PHPStan no está instalado. En Windows se definió `PHPRC` para que los subprocesos también usaran el php.ini de validación.

`composer install` completó la verificación del lock, la generación del autoload optimizado y package discovery. Se repitieron las comprobaciones del backend después de terminar Composer, con resultado correcto. Los contenedores temporales de validación se retiraron al finalizar.

PHPUnit se invoca directamente para evitar que `artisan test` añada otra opción `--configuration`. La verificación de servicios se ejecuta en un proceso previo, evitando inicializar Laravel dos veces durante las pruebas.

Esta validación reproduce los comandos localmente; no equivale a una ejecución remota de GitHub Actions. No se realizó commit ni push.
